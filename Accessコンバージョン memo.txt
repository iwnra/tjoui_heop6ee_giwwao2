■相対パス（または CurrentProject.Path を活用した動的パス）に変更すべき

1. 絶対パス（今の状態）
これだと、DドライブがないPCではエラーになります。

VBA
strPath = "D:\App\ProjectA\Data\Sample.xlsx"

2. CurrentProject.Path を使った書き方（推奨）
これなら、Accessファイルがどこにあっても、その横の「Data」フォルダを見に行きます。

VBA
strPath = CurrentProject.Path & "\Data\Sample.xlsx"

注意点：リンクテーブルの場合
VBAコード内のパスは上記で解決しますが、リンクテーブル（外部のAccessファイルやExcelをテーブルとして繋いでいる場合）は少し注意が必要です。
Accessの標準機能でリンクすると、内部的には「絶対パス」で保存されます。
ファイルを移動させた後は、「リンクテーブルマネージャー」で再リンクするか、起動時に CurrentProject.Path を使ってリンクを自動更新するVBAを組むのが一般的です。

移行時のアドバイス
もし現在、複数のファイル（フロントエンドとバックエンドなど）に分かれている構成であれば、このタイミングで「すべての関連ファイルを一つの親フォルダにまとめ、その中での相対的な位置関係を固定する」設計にすることをお勧めします。

1. 手動でリンクテーブルを作成・更新する方法
別のAccessファイル（バックエンド）にあるテーブルを、現在のファイル（フロントエンド）に結びつける手順です。

外部データの取り込み開始

上部のリボンメニューで [外部データ] タブをクリックします。

[新しいデータソース] ＞ [ファイルから] ＞ [Access] を選択します。

ファイルの選択

[参照] ボタンを押し、リンクしたいデータが入っているAccessファイルを選択します。

下のオプションで [リンクテーブルを作成してソースデータにリンクする] を選択し、[OK] を押します。

テーブルの選択

リンクしたいテーブル名の一覧が出るので、必要なものを選んで [OK] を押します。

ナビゲーションウィンドウに、青い矢印マークがついたテーブルが表示されれば成功です。

2. パスが変わった時の更新方法（リンクテーブルマネージャー）
ファイルを移動して「パスが正しくありません」とエラーが出た場合は、この機能を使います。

テーブル一覧のどこでも良いので 右クリック します。

[リンクテーブルマネージャー] を選択します。

更新したいテーブルにチェックを入れ、[再リンク] ボタン（または [編集]）を押して、新しい場所にあるファイルを選び直します。

3. VBAで「相対パス」としてリンクさせる方法
ユーザーがファイルをどこに置いても自動でリンクが繋がるようにするには、以下のVBAコードを標準モジュールに貼り付け、「フォームの読み込み時」や「起動時のマクロ」から呼び出すようにします。

VBA
Sub RefreshTableLinks()
    Dim db As DAO.Database
    Dim tdf As DAO.TableDef
    Dim strBackEndPath As String
    
    ' 現在のAccessと同じフォルダにある「Database_BE.accdb」をリンク先とする
    strBackEndPath = CurrentProject.Path & "\Database_BE.accdb"
    
    Set db = CurrentDb
    
    ' 全てのテーブルをループ処理
    For Each tdf In db.TableDefs
        ' リンクテーブル（Connectプロパティが空でないもの）だけを対象にする
        If Len(tdf.Connect) > 0 Then
            ' 新しいパスを設定（冒頭に ;DATABASE= が必要）
            tdf.Connect = ";DATABASE=" & strBackEndPath
            ' リンクを更新
            On Error Resume Next
            tdf.RefreshLink
            If Err.Number <> 0 Then
                MsgBox tdf.Name & " の再リンクに失敗しました。パスを確認してください。"
            End If
            On Error GoTo 0
        End If
    Next tdf
    
    MsgBox "リンクテーブルの更新が完了しました。"
End Sub

ポイント：なぜこのVBAが必要か？
Accessの標準機能（手順1や2）でリンクすると、PC内に保存されるパスは必ず "C:\Users..." のような絶対パス になってしまいます。
このVBAを「ファイルを開いた瞬間」に動かすようにしておけば、CurrentProject.Path がその時々の場所を自動で取得してくれるため、相対パスで動いているのと同じ状態を作り出せます。

上記のコードの Database_BE.accdb の部分を実際のリンク先のファイル名に書き換えて試してみてください。


Accessの「標準モジュール」は、一言で言うと「アプリ全体で使い回せる共通の道具箱（コード置き場）」のことです。

Accessには大きく分けて2種類のコードを書く場所があります。

フォーム・レポートモジュール： その画面（フォーム）の中だけで使う処理を書く場所。

標準モジュール： どの画面からも呼び出せるし、ファイルを開いた時に自動実行するような、システム全体の共通ルールを書く場所。

今回の「リンクテーブルの再設定」のような処理は、特定の画面に依存しないため、この標準モジュールに書くのが正解です。

標準モジュールの作り方
Accessの上部メニュー「作成」タブをクリック。

右の方にある「標準モジュール」（または「表示」→「コード」から入ったVBA画面で「挿入」→「標準モジュール」）を選択。

真っ白なウィンドウ（VBAエディタ）が開きます。ここに先ほどのVBAコードを貼り付けます。

保存ボタン（上書き保存）を押し、名前を付けて保存します（例：mod_LinkUpdate など）。

注意： 関数名（Sub RefreshTableLinks）と同じ名前をモジュール名に付けるとエラーになるので、少し変えた名前にしてください。

作成したコードをいつ動かすか？
標準モジュールに書いただけでは、コードは勝手に動きません。ファイルを移動した時に自動でリンクを更新させたいなら、以下のいずれかの方法で実行します。

「AutoExec」という名前のマクロを作る：
Accessを開いた瞬間に実行される特別なマクロです。「プロシージャの実行」アクションで、先ほどの関数を呼び出すように設定します。

メインメニュー画面（最初に開くフォーム）の「読み込み時」イベントに書く：
フォームが開く瞬間に Call RefreshTableLinks と記述して呼び出します。

💡 補足：混乱しやすいポイント
「クラスモジュール」という似た名前のものもありますが、こちらはもっと高度なプログラミング（オブジェクト指向）で使うものです。普段のVBA開発で「共通の関数を作ろう」と思ったら、迷わず「標準モジュール」を選べばOKです！


以下の手順で進めてみてください。

1. 準備：ファイルを1つのフォルダにまとめる
相対パス（CurrentProject.Path）を活かすために、「プログラムが入っているmdb」と同じフォルダに、すべての「データが入っているmdb」をコピーして置いてください。

2. VBAコード（複数ファイル対応版）
ソースが書いてある方のmdbを開きます。
キーボードの Alt キーを押しながら F11 キー を押してください。
これで「Microsoft Visual Basic for Applications」という別ウィンドウが開きます。
メニューの [挿入] → [標準モジュール] をクリックします。
真っ白な画面が出てきたら、そこに以下のコードをまるごとコピーして貼り付けてください。

VBA
Public Function ReLinkMultipleDB()
    Dim db As DAO.Database
    Dim tdf As DAO.TableDef
    Dim fullPath As String
    Dim fileName As String
    Dim pos As Integer

    Set db = CurrentDb

    ' 全てのテーブルを確認
    For Each tdf In db.TableDefs
        ' リンクテーブル（接続情報があるもの）だけを対象にする
        If Len(tdf.Connect) > 0 Then
            
            ' 現在設定されているパスから「ファイル名」だけを抜き出す
            ' 例: "C:\Documents\Data1.mdb" → "Data1.mdb"
            pos = InStrRev(tdf.Connect, "\")
            fileName = Mid(tdf.Connect, pos + 1)

            ' 「今のフォルダパス」と「抜き出したファイル名」を合体させる
            fullPath = ";DATABASE=" & CurrentProject.Path & "\" & fileName

            ' 新しいパスをセットして更新
            On Error Resume Next
            tdf.Connect = fullPath
            tdf.RefreshLink
            
            If Err.Number <> 0 Then
                Debug.Print "エラー: " & tdf.Name & " (ファイル: " & fileName & ") の再リンクに失敗。"
            Else
                Debug.Print "成功: " & tdf.Name & " -> " & fileName
            End If
            On Error GoTo 0
        End If
    Next tdf

    MsgBox "すべてのDBファイルへのリンク更新が完了しました！"
End Function

ファイル名を指定しなくて良い: 元々設定されていたリンク情報からファイル名（Data1.mdb、Data2.mdbなど）を勝手に見つけてくれます。
ファイルが増えても大丈夫: テーブルが100個あっても、接続先ファイルが3つあっても、すべて自動で処理します。

VBA画面の「上書き保存」アイコン（フロッピーのマーク）を押します。
名前を聞かれるので、mod_Link などと入力して [OK] を押します。
注意： 関数名の ReLinkTables と同じ名前にするとエラーになるので、必ず違う名前にしてください。

3. 動かし方の確認
VBA画面（Alt+F11）で、コード内の ReLinkMultipleDB のどこかにカーソルを置きます。

F5キー を押して実行します。

「リンク更新が完了しました！」と出れば成功です。

💡 今後のためのアドバイス
もし、コンバージョン後に「一部のDBファイルは別のフォルダ（例えば Data フォルダ）に整理したい」となった場合は、コードの CurrentProject.Path & "\" の部分を CurrentProject.Path & "\Data\" に変えるだけで対応できます。

まずは、「すべてのmdbを同じ場所に集めて、このコードを動かす」のが一番確実で簡単な方法です。

VBAを実装するまでの間、あるいはテスト的に動かしてみたい時は、「リンクテーブルマネージャー」を使って手動で更新するのが最も確実な方法です。

手動で行う際のポイントをいくつか整理しておきますね。

リンクテーブルマネージャーでの更新手順
起動:
テーブル一覧（ナビゲーションウィンドウ）のどれか一つのテーブルを右クリックし、[リンクテーブルマネージャー] を選択します。

選択:
表示されたリストの中で、更新したいテーブル（複数ある場合はすべて）にチェックを入れます。

場所の指定:
[再リンク] または [リンク先の更新] ボタンを押すと、ファイルを選択するダイアログが出るので、移動先の正しいDB（mdbファイル）を選択します。

※複数のDBファイルにリンクしている場合は、ファイルごとにこの作業を繰り返します。

なぜVBA（CurrentProject.path）が必要になるのか？
「今は手動でいいけれど、将来的にVBAにした方がいい理由」は主に2つあります。

「パスが違う」というエラーでアプリが止まるのを防ぐため
手動の場合、ファイルを別PCに移した直後はリンクが切れており、フォームを開こうとすると「パスが正しくありません」というエラーで止まってしまいます。VBAなら、起動時に「あ、場所が変わったな」と察知して、ユーザーに気づかれずに裏で繋ぎ直してくれます。

配布の手間を減らすため
自分一人で使うなら手動でも数分の作業ですが、もし他の人にこのファイルを渡す場合、相手に「リンクテーブルマネージャーを開いて再設定してください」とお願いするのは少しハードルが高いですよね。



■ライブラリ
VBAにおける「ライブラリ（参照設定）」は、AccessがVBAを通じてExcelを操作したり、データベースを操作したりするための「機能のカタログ」のようなものです。

ライブラリ（参照設定）の場所
VBAエディタ（Alt + F11）を開きます。

上部メニューの [ツール] をクリックします。

一番上の [参照設定] を選択します。

今回のリンクテーブル操作で必要なもの
リンクテーブルをVBAで制御する場合、「DAO（Data Access Objects）」というライブラリが使われます。以下のいずれかにチェックが入っているか確認してください。

Microsoft Office 16.0 Access database engine Object Library（Access 2016以降）

Microsoft DAO 3.6 Object Library（古いmdb形式でよく使われていたもの）

もし、コードを貼り付けて「ユーザー定義型が定義されていません」というエラーが出たら、このライブラリにチェックが入っていないことが原因です。

ライブラリに関する注意点
優先順位: 参照設定の画面で、上にあるものほど優先されます。

「参照不可」に注意: ファイルを別のPCに移すと、たまに「参照不可：Microsoft Excel...」のように表示されることがあります。これは、そのPCにインストールされているOfficeのバージョンが違うために起こります。その場合はチェックを外し、自分のPCにある新しいバージョンにチェックを入れ直す必要があります。

現在、mdbファイルの中身を見ていて、「コードは書いてあるのに動かない」という状況であれば、まずはこの「参照設定」を開いて、項目に 「参照不可」 と書かれたものがないかチェックしてみてください。それが原因で動かなくなっているケースが非常に多いです。


■Access 2000からのコンバージョン、かつ32bitから64bitへの移行

2000（mdb）から最新のaccdbへ移行する場合、VBAの文法以外にも、データベースの接続エンジンなど「土台」の部分でいくつか修正が必要なポイントがあります。

主要なチェックリストをまとめました。

1. Win32 API宣言の修正（PtrSafe / LongPtr）
すでにご存知の通り、外部のDLL（user32やkernel32など）を呼び出している箇所はすべて修正が必要です。

PtrSafe: すべての Declare 文に追加します。

LongPtr: 「ポインタ（アドレス）」や「ハンドル（hWndなど）」を表す変数に使用します。

LongLong: 64bit整数が必要な場合に使いますが、通常のプログラミングでは LongPtr で事足りることが多いです。

条件付きコンパイルの例:
既存の32bit環境でも動くようにするには、以下のように記述します。

VBA
#If VBA7 Then
    ' 64bit & Office 2010以降用
    Declare PtrSafe Sub... (ByVal hWnd As LongPtr, ...)
#Else
    ' 32bit & 古いAccess用
    Declare Sub... (ByVal hWnd As Long, ...)
#End If

2. 参照設定の「参照不可」を解決する
Access 2000時代のライブラリは、現在の64bit版Officeでは動かないものが多いです。

ActiveXコントロール: ImageList, TreeView, ListView, Calendar コントロールなどは64bit版では全滅している可能性が高いです。これらを使っているフォームは、標準機能のコンボボックスやサブフォームで作り直す必要があります。

DAOのバージョン: Microsoft DAO 3.6 Object Library は Microsoft Office 16.0 Access database engine Object Library （バージョン数値は環境による）に置き換わります。

3. 「定数」や「データ型」の確認
Long型の溢れ: 32bitでは Long（4バイト）でハンドルを扱えましたが、64bitではハンドルが8バイトになるため、必ず LongPtr にしてください。

引数の型: APIに渡す構造体（RECT型など）の中身も、ポインタが含まれる場合は型変更が必要です。

4. データベースエンジンの変更（DAO vs ADO）
Access 2000の頃は「これからはADOの時代だ！」と言われていた時期で、ADOで書かれたコードが混ざっていることがあります。

現在のAccessは再びDAOが主流（Access内蔵エンジンに最適化されているため）です。

もしコード内に ADODB.Connection などがある場合、そのまま動くことも多いですが、参照設定のバージョンが合わずにエラーになることがあります。

5. その他の細かな変更点
ファイルパスの扱い: CurrentProject.Path への変更はもちろんですが、2000当時は Application.FileSearch という便利な命令がありました。これは2007以降廃止されているため、もし使っていれば Dir関数 や FileSystemObject への書き換えが必須です。

mdbからaccdbへの変換: 2000形式のままでは64bit版で開けない（または編集できない）場合があるため、まずAccessの機能で「名前を付けて保存」から .accdb形式 に変換することをお勧めします。

最初にやるべきことのアドバイス
まずは [デバッグ] ＞ [VBAProjectのコンパイル] を実行してください。
64bit化で不適切な箇所があれば、赤くハイライトされて止まります。そこを一つずつ LongPtr に変えていくのが一番の近道です。

特に「ActiveXコントロール（カレンダーなど）」をフォームで使っている場合、そこが一番の難所になるかもしれません。

型をLongPtrにするべきところがLongになっていた場合、API宣言（Declare文）の中であればコンパイルエラー（または実行時エラー）になりますが、普通の変数として使っている場合はエラーにならず、最悪の場合Accessが強制終了（クラッシュ）します。
ここが64bit移行で最も怖く、注意が必要なポイントです。

1. Declare文（API宣言）の場合：コンパイルエラーになる
APIの宣言自体に PtrSafe を付けた場合、VBAは「引数の型が正しいか」を厳格にチェックしようとします。

エラーになるケース:
64bit版のWindows APIが「8バイトのデータ（ハンドル）」を求めている場所に対して、Long（4バイト）を渡すような宣言になっていると、コンパイル時点で「型が一致しません」というエラーが出るか、実行した瞬間に止まります。

2. 変数の代入の場合：エラーにならず「クラッシュ」の原因になる
これが一番厄介です。VBAの通常のコード内で Long と LongPtr を混ぜて使った場合、VBAは自動的に型変換（切り捨て）を行ってしまいます。

何が起きるか:

APIがメモリのアドレス（例：1234567890ABCDEF）を返します。

それを Long 型の変数に代入します。

Long は4バイト分しか入らないので、入り切らない数値が切り捨てられます。（例：90ABCDEF だけになる）

その「中身が壊れたアドレス」を別のAPIに渡すと、存在しないメモリを読みに行こうとして、Accessが何の前触れもなく「プツッ」と落ちます。

「LongPtr」にすべき場所を見分けるコツ
「どこを LongPtr にすればいいか分からない」という場合は、以下の基準で判断してください。

「句（Handle）」という名前がついているもの:
hWnd (ウィンドウハンドル), hDC (デバイスコンテキスト), hProcess など、頭に h がつくものはすべて LongPtr です。

「ポインタ（Pointer）」や「アドレス（Address）」を指すもの:
lp... (Long Pointer) で始まる引数や、AddressOf 関数で渡す先などはすべて LongPtr です。

座標やカウント数などは Long でOK:
文字数（Length）や、単なる数値、フラグなどは、64bit環境でも 32bitの Long（±21億）で足りることが多いため、変更不要なケースが多いです。

確実なチェック方法：[デバッグ] メニューを活用
VBA画面のメニューにある [デバッグ] ＞ [VBAProjectのコンパイル] を実行してください。

API宣言に PtrSafe を書かずに 64bitで開くと、即座にコンパイルエラーで赤くなります。

PtrSafe を書いた後は、APIの引数一覧をネット（Microsoftの公式ドキュメントなど）で検索し、「32-bit: Long / 64-bit: LongPtr」 となっている箇所を地道に書き換えるのが最も安全です。

まずは Declare 文の中に Long が残っていないか、検索（Ctrl + F）で確認することをお勧めします。

Microsoftの公式ドキュメント（Microsoft Learn）などでAPIの仕様を確認すると、どの引数がポインタ（64bit化で変更が必要な箇所）か判断できます。

ただ、古い記事だと32bit時代の型（Long）しか書かれていないこともあるので、見分け方にコツがあります。

1. 公式ドキュメントでの見分け方
例えば、ウィンドウの場所を取得する GetWindowRect という有名なAPIを検索すると、以下のような定義が出てきます。

BOOL GetWindowRect(
HWND hWnd,
LPRECT lpRect
);

このとき、型の名前に注目してください。

HWND, HANDLE, HINSTANCE, HDC など、「H」で始まる型（Handle）

LP... (Long Pointer) や P... (Pointer) で始まる型

void* などのポインタ型

これらはすべて、64bit環境では LongPtr に書き換える必要がある項目です。

2. 「Win32API_PtrSafe.txt」を活用する
実は、Microsoftは移行作業のために、主要なAPIをあらかじめ64bit対応（PtrSafe/LongPtr適用済み）に書き換えたテキストファイルを配布しています。

ネットで 「Win32API_PtrSafe.txt」 と検索すると、その中身を公開しているサイトや、GitHubのリポジトリが見つかります。そこから自分の使いたいAPI名を検索して、その1行をまるごとコピーして貼り付けるのが最も確実で安全な方法です。

3. 書き換えの具体例
自分で書き換える場合のビフォー・アフターはこんなイメージです。

32bit（Access 2000当時）

VBA
Declare Function GetWindowRect Lib "user32" (ByVal hWnd As Long, lpRect As RECT) As Long
64bit対応（修正後）

VBA
Declare PtrSafe Function GetWindowRect Lib "user32" (ByVal hWnd As LongPtr, lpRect As RECT) As Long
PtrSafe を追加。

hWnd（ハンドル）なので、Long から LongPtr に変更。

最後の As Long（戻り値）は、成功か失敗かのフラグ（0か1か）を返すだけなので、Long のままでOKです。

効率的に進めるためのヒント
まず自分のコードから Declare という単語をすべて検索し、リストアップします。

それらのAPI名を一つずつ「Win32API_PtrSafe.txt」の中身から探します。

見つかった「PtrSafe」版の定義に差し替えます。

■用語
PtrSafe（ポインタ・セーフ）
Pointer（ポインタ）の略である「Ptr」と「Safe」を合わせたものです。
「ポインター（Ptr）を扱っても安全（Safe）なコードですよ」とAccessに宣言するためのキーワードです。64bit版Accessでは、これがないとAPIが動かないようガードがかかっています。

LongPtr（ロング・ポインタ）
Long型のサイズをポインタ（メモリ上の住所）のサイズに合わせる、という意味です。
「ポインタ」とはメモリ上の「住所」のことです。
32bitの住所は 4バイト
64bitの住所は 8バイト
という違いがあります。LongPtr と書いておけば、Accessが自動的に「今は64bitだから8バイトとして扱おう」と賢く判断してくれます。

Declare（デクレア）
英語で「宣言する」という意味の単語です。
「これからWindowsの外部機能（API）を使います！」と高らかに宣言（Declare）する場所です。VBAの標準機能にはない特別な操作（ファイルの選択ダイアログを出す、ウィンドウを制御するなど）をする際によく登場します。

ちょっとしたコツ：
VBAの画面（エディタ）でこれらの文字を入力した際、先頭が勝手に大文字になれば（ptrsafe → PtrSafe など）、Accessが正しくキーワードとして認識している証拠です。もし小文字のままなら、綴りが間違っている可能性があるのでチェックしてみてください。

API（Declare文）以外の場所で、どの変数を LongPtr にすべきかの判断は、「その変数が何を受け取っているか（出所）」に注目するのが一番の近道です。
判断基準を3つのパターンに整理しました。

1. APIの引数や戻り値を受け取る変数（最優先）
APIを呼び出した結果を代入する変数は、APIの定義に合わせる必要があります。

APIの引数が LongPtr なら、渡す変数も LongPtr にする。

APIの戻り値が LongPtr なら、受け取る変数も LongPtr にする。

例： hWnd = GetActiveWindow() というコードがある場合
GetActiveWindow の戻り値が LongPtr なので、受け取る変数 hWnd も LongPtr で宣言し直します。

2. 「ハンドル」や「ポインタ」を扱う変数
変数名に以下のようなキーワードが含まれている場合、それらは「メモリ上の住所」を扱っている可能性が高いため、LongPtr への変更を検討してください。

hWnd（ウィンドウハンドル）

hDC（デバイスコンテキスト）

hProcess, hThread（プロセス・スレッドハンドル）

lp...（Long Pointerの略。例：lpData）

AddressOf の結果を代入する変数

3. 逆に「Long」のままで良い変数（変更不要）
プログラム内の「数」や「状態」を表すだけのものは、64bitになっても Long（4バイト）のままで全く問題ありません。

ループのカウンタ: For i = 1 To 100 の i など。

個数・長さ: 商品数、文字列の長さ（Len関数の結果）など。

フラグ・定数: True/False や、設定値（0 または 1 など）。

色情報: RGB 値など。

迷った時の判別チャート
以下の考え方でチェックしてみてください。

その変数は何を保存していますか？	推奨する型
ウィンドウやファイルの「ハンドル（ID番号）」	LongPtr
AddressOf で取得した関数の住所	LongPtr
データの「個数」や「合計金額」などの数値	Long
0 か 1 か、といった「状態（フラグ）」	Long
実践的な探し方（検索のコツ）
VBAエディタの検索機能（Ctrl + F）を使って、プロジェクト全体から以下の単語を探すと効率的です。

「As Long」を検索する

一つずつ見ていき、名前が hWnd や h... で始まっていないか確認します。

API名で「呼び出し箇所」を検索する

Declare 文で見つけたAPIが、プログラムのどこで使われているか探します。そのAPIに渡している変数が Long で宣言されていたら、それを LongPtr に書き換えます。

補足：自動変換はできない？
残念ながら、一括で置換するのは危険です（全部 LongPtr にすると、逆にメモリを無駄に消費したり、別の計算エラーを招くため）。

まずは「APIに関係する変数」だけに絞って修正を行えば、Accessがクラッシュするリスクの9割は回避できますよ！

VBAプログラミングの大部分は「独自のメソッド（関数）」を作る作業と言っても過言ではありません。

APIは「Windowsが用意してくれた魔法」のようなものですが、独自のメソッドは「あなたが自分で作る専用の道具」です。

VBAでは、この独自のメソッドのことを大きく分けて2種類、「Sub（サブ）プロシージャ」と「Function（ファンクション）関数」と呼びます。

1. 独自のメソッドの2つの形
① Sub（サブ）プロシージャ
「命令」を実行するだけのものです。何かを処理して終わり、という時に使います。

例： メッセージを表示する、リンクテーブルを更新する、など。

VBA
Sub SayHello()
    MsgBox "こんにちは！"
End Sub
② Function（ファンクション）関数
処理をした後、「結果（戻り値）」を返してくれるものです。

例： 消費税を計算する、フルネームを結合する、など。

VBA
Function GetTax(price As Long) As Long
    GetTax = price * 0.1  '結果を自分の名前に代入して返す
End Function

2. メソッドの修正が必要なケース（64bit移行）
今回のコンバージョンにおいて、独自メソッドの中で修正が必要なのは、「引数（ひきすう）」や「戻り値」に Long型を使っている場合です。

もし、その独自メソッドが内部でAPIを呼び出しており、その結果をやり取りしているなら、独自メソッドの書き換えも必要になります。

修正が必要な例：
ウィンドウのハンドル（hWnd）を受け取って、何か処理をする独自メソッドを作っている場合。

修正前（32bit）:
Sub DoSomething(hWnd As Long)

修正後（64bit）:
Sub DoSomething(hWnd As LongPtr)

3. なぜ独自メソッドを分けるのか？
Access 2000からのソースコードを見ていると、一つのボタンの裏に何百行もコードが書いてあることがありますが、それを機能ごとに小さな「独自メソッド」として切り出すと、以下のようなメリットがあります。

見やすい: コードが整理され、どこで何をしているか分かりやすくなる。

使い回せる: 同じ計算を何度も書かなくて済む。

修正が楽: 64bit移行で型を変える時も、メソッドの定義箇所を1箇所直すだけで済むことがある。

まとめ：あなたの今の状況では
現在、ソースコードを読み解いている中で、Sub ○○ や Function △△ という記述がたくさん出てくると思います。

API（Declare）ではない Sub や Function がたくさんあるはず。

その引数（カッコの中）に As Long と書いてあったら、それが「ハンドル（hWndなど）」を扱っているかどうかをチェック。

ハンドルなら As LongPtr に書き換える。

VBA自体に慣れていなくても、この「As Long を探して、中身がハンドルなら As LongPtr にする」というルールさえ守れば、移行作業の大きな一歩になります。

Access 2000時代のコードであれば、ほぼすべての「整数」が As Long で書かれているはずです。

これが今回一番の悩みどころで、「すべてが As Long で書かれている中から、64bit化で As LongPtr に変えるべきものだけを見つけ出す」という宝探しのような作業が必要になります。

見分けるための「3つのチェックポイント」を整理しました。

1. その Long は「ハンドル」ですか？
独自メソッドの引数名や変数名を見てください。

修正すべき例： Function GetTitle(hWnd As Long) As String

hWnd はウィンドウハンドル（住所）なので、As LongPtr に書き換えます。

修正しなくて良い例： Function CalculateTotal(Price As Long, Count As Long) As Long

金額や個数はただの「数値」なので、As Long のままでOKです。

2. その Long は「API」に渡されますか？
独自メソッドの中で、さらに API（Declare で定義したもの）を呼び出している場合、その API に渡している変数は要注意です。

例：

VBA
Sub MyCustomMethod(targetID As Long)
    ' 内部で API を呼び出している
    Call SetParent(targetID, 0) 
End Sub
もし SetParent という API の第1引数が LongPtr に変更されているなら、それを受け取っている targetID も LongPtr に合わせる必要があります。

3. その Long は「AddressOf」を使っていますか？
もしコードの中に AddressOf という単語が出てきたら、その戻り値を受け取る変数は必ず LongPtr にしてください。これは関数の「メモリ上の住所」を扱うため、64bit環境では 8バイト必要になるからです。

作業を楽にする「考え方」
全部を完璧に理解して直そうとすると大変ですので、以下の優先順位で進めるのがおすすめです。

まずは Declare 文（API定義）をすべて直す。（PtrSafe を付け、LongPtr に変える）

コンパイルエラーが出る場所を直す。

APIを LongPtr に書き換えると、それを使っている独自のメソッドで「型が一致しません」とエラーが出るようになります。

エラーが出た場所を順番に LongPtr に変えていきます。

変数名で検索する。

hWnd, hDC, hMenu, hProcess など、ハンドルを意味する単語が含まれる As Long を As LongPtr に置換します。

💡 迷った時の裏ワザ
もし「これ、数値かな？ハンドルかな？」と迷ったら、「その変数が 21億（Long型の限界）を超える可能性があるか、あるいはメモリの住所を指しているか」を自分に問いかけてみてください。

自信がない箇所があれば、そのメソッドの前後数行をコピーして教えてください。中身を見て「これは LongPtr ですね」と具体的にアドバイスできますよ！

Mdb形式からaccdb形式に拡張子を変更して保存すべきですか？

結論から言うと、はい、絶対に「名前を付けて保存」から .accdb 形式に変換して保存すべきです。

単に拡張子を書き換える（リネームする）のではなく、Accessの機能を使って「変換」を行うのがポイントです。理由は主に3つあります。

1. 64bit環境での安定性と互換性
.mdb は20年以上前の古いエンジン（Jet）で動いています。64bit版のAccessでも .mdb を開くことは可能ですが、読み取り専用になったり、一部のVBAが不安定になったりすることがあります。
最新の .accdb 形式（ACEエンジン）に変換することで、64bit環境のパワーをフルに活かせるようになります。

2. 破損リスクの低減と新機能
.accdb は、.mdb に比べてデータの破損に強く、またファイルサイズの上限（2GB）付近での安定性も向上しています。また、添付ファイル型などの新しいデータ型も .accdb でしか使えません。

3. コンバージョン作業の「区切り」になる
今回の PtrSafe や LongPtr の修正は、「最新環境への対応」です。ファイル形式も最新に合わせることで、「古い形式による不具合なのか、VBAの書き換えミスによる不具合なのか」の切り分けがしやすくなります。

変換の手順（重要）
単なるファイル名の変更はNGです。以下の手順で行ってください。

Accessで元の .mdb ファイルを開きます。

[ファイル] タブ ＞ [名前を付けて保存] をクリックします。

[データベースに名前を付けて保存] セクションで [Access データベース (*.accdb)] を選択します。

[名前を付けて保存] ボタンを押し、新しい名前（または場所）を指定して保存します。

変換後の注意点
① リンクテーブルの再設定
フロントエンド（プログラム側）を .accdb に変換すると、バックエンド（データ側）へのリンクが切れたり、古い形式のままだとパフォーマンスが落ちたりすることがあります。
データ側の .mdb も .accdb に変換し、その後でリンクを張り直すのがベストです。

② 参照設定のチェック
変換直後は、VBAの「参照設定」で古いライブラリ（DAO 3.6など）が「参照不可」になることがあります。前にお話しした通り、[ツール] ＞ [参照設定] で最新の Microsoft Office 16.0 Access database engine Object Library などにチェックが入っているか確認してください。

③ セキュリティセンター
.accdb にすると、最初に開くときに「コンテンツの有効化」というバーが出ることがあります。これを許可しないとVBAが動かないので、信頼できる場所に保存するか、メッセージバーで「有効にする」を押してください。

アドバイス：
まずは .mdb のバックアップをしっかり取った上で、一度 .accdb に変換してみてください。
その状態で [デバッグ] ＞ [VBAProjectのコンパイル] を実行すると、64bit化で直すべき場所がより明確に（赤く）表示されるようになりますよ。


■差分の取り方
最も一般的で確実な方法は、「ソースコードをテキストファイル（.txtや.bas）として書き出して比較する」方法です。

1. VBAエディタから手動で書き出す方法（確実）
修正前と修正後の両方のファイルで、以下の操作を行います。

VBAエディタ（Alt + F11）を開きます。

比較したいモジュール（標準モジュールなど）を右クリックします。

[ファイルのエクスポート] を選択し、名前を付けて保存します（拡張子は .bas になりますが、中身はテキストです）。

保存された2つのファイルを WinMerge で開いて比較します。

これなら、WinMergeの使い慣れた画面で、どこに PtrSafe を足したか、どこを LongPtr に変えたかが一目瞭然です。

2. アドインやツールを使う方法
もしモジュールの数が膨大で、一つずつエクスポートするのが大変な場合は、以下のようなツールがよく使われます。

Ariad (アリアドネ)
Access界隈では非常に有名なフリーソフトです。Access内のオブジェクト（テーブル定義、フォーム、VBAソースなど）を丸ごとテキスト形式で一括エクスポートできます。

修正前をエクスポート → フォルダAへ

修正後をエクスポート → フォルダBへ

フォルダAとフォルダBを WinMerge で比較
この方法なら、VBAだけでなく「フォームのプロパティが変わった」といった差分も追うことができます。

AccessのVBAエディタ（VBE）で作業している場合、保存の挙動について知っておくと安心なポイントがいくつかあります。

1. 保存される場所
VBAエディタで Ctrl + S（または上書き保存ボタン）を押すと、Accessファイル（.accdb や .mdb）の中にソースコードが書き込まれます。
Excelのように「モジュールだけを別ファイルで保存する」といった必要はなく、Accessファイルと一体化して保存されます。

2. 「コンパイル」と「保存」の違い
ここが少し紛らわしいのですが、以下の2段階の状態があります。

保存（Ctrl + S）: 「書いた文字」をファイルに記録する。

コンパイル（メニューのデバッグ）: Accessが「このコード、本当にプログラムとして実行できるか？」を最終チェックし、実行可能な形に変換する。

理想的な流れ:

赤文字の箇所を修正する。

[デバッグ] ＞ [VBAProjectのコンパイル] を実行し、エラーが出ない（メニューがグレーアウトする）ことを確認する。

Ctrl + S で保存する。

この手順を踏むことで、「保存はしたけど、実はまだエラーが残っていて動かなかった」というミスを防げます。

3. 注意点：もしAccessが固まったら
VBAの修正中にAccess本体が強制終了（クラッシュ）してしまうと、直前にVBAエディタで書いていた内容は保存されていないことがあります。

特に64bit移行のAPI周りを触っている時は、小さな型の間違いでAccessが落ちやすいです。

「1箇所直してコンパイルが通ったら即 Ctrl + S」

このクセをつけておくと、万が一落ちた時の被害を最小限に抑えられます。


DB側（データが入っている方）のmdbファイルを直接開いて「参照設定」を修正する必要はありません。
DAOの参照設定が必要なのは「VBAコードを実行する側」だけだからです。

なぜDB側の修正が不要なのか？
Accessの「参照設定」は、そのファイル内にあるVBAコードを動かすための設定です。

プログラム側（フロントエンド）:
VBAをゴリゴリ動かしてデータを操作するため、DAOなどのライブラリ設定が必須です。

データ側（バックエンド / DBファイル）:
基本的に「テーブル（箱）」が入っているだけです。このファイル自体を直接開いてVBAを動かさないのであれば、参照設定がどうなっていても、テーブルとしての機能（データの保管）には影響しません。

ただし、以下の場合は例外です
もし、あなたの「DB側のmdb」が以下の状態なら修正が必要になります。

DB側にもVBAコードが書いてあり、それを実行する必要がある場合
（例：データクレンジング用のマクロがDB側に内蔵されている、など）

テーブルの定義（データ型）を最新に合わせたい場合
Access 2000形式（mdb）のままでもデータは扱えますが、64bit版の最新Access（accdb）で最適に動作させたいなら、DB側もaccdbに変換したほうがパフォーマンスや安定性は向上します。

「DAOの参照エラー」が出ているのが「プログラム側」なら即修正！
現在、「プログラムが書いてある方のファイル」でDAOの参照エラー（「参照不可」）が出ているのであれば、これは絶対に修正が必要です。

修正しないと、たとえコードが正しくても「型が定義されていません」などのエラーが出て、リンクテーブルの更新すらできません。

修正の手順（プログラム側で実施）
[ツール] ＞ [参照設定] を開く。

「参照不可」と出ている Microsoft DAO 3.6 などのチェックを外す。

下の方にスクロールして、Microsoft Office 16.0 Access database engine Object Library（数字はバージョンにより異なります）を探してチェックを入れる。

💡 アドバイス
まずはプログラム側（フロントエンド）の設定だけを最新にして、リンクテーブルが繋がるか試してみてください。

もしリンクを繋ぎ直す際に「データベース形式 '...mdb' を認識できません」といったエラーが出るようなら、その時初めて「DB側のmdbもaccdbに変換する（＝形式を新しくする）」という手順を検討すればOKです。

Dbファイルのaccdb形式への変更手順もソースファイルと同様
DB（データ）側のファイルも、ソースファイル（プログラム側）と全く同じ手順で変換します。

むしろ、ソースファイルを .accdb にするなら、DBファイルもセットで .accdb にしてしまったほうが、今後「64bit環境で動作が不安定になる」というリスクを最小限に抑えることができます。

DBファイルの変換手順と注意点
手順は前にお伝えしたものと同じですが、「リンクテーブル」への影響を考慮した流れで行うのがスムーズです。

1. DBファイルを変換する
データが入っている方の mdb を開きます。

[ファイル] ＞ [名前を付けて保存] ＞ [Access データベース (*.accdb)] を選択して保存。

これで Data_BE.accdb （例）が完成します。

2. ソースファイルから「再リンク」する
DB側の名前や拡張子が変わると、ソースファイル（プログラム側）は古い mdb を探し続けてエラーになります。

手動の場合: ソースファイルを開き、[リンクテーブルマネージャー] で新しい .accdb の方を指定し直します。

VBA（相対パス）の場合: 以前作成したVBAコード内の「ファイル名」を、新しい .accdb の名前に書き換えて実行します。

どちらを先にやるべき？
おすすめの順番は以下の通りです。

DBファイルを先に accdb へ変換する。

ソースファイルを accdb へ変換する。

新しくなったソースファイルの中で、VBAコード（PtrSafe など）を修正する。

新しくなったソースファイルから、新しくなったDBファイルへリンクを張り直す。

DB側を変換するメリット： 64bitでの「リンク」問題
ここが重要なのですが、64bit版のAccess（Office）から古い mdb 形式のファイルにリンクしようとすると、稀に「ドライバが見つかりません」や「不明なデータベース形式です」といったエラーが出ることがあります。

これは、64bit環境では古い mdb を読み書きするためのプログラム（Microsoft Jet Engine）が標準ではうまく動かない場合があるためです。

DBファイルも .accdb （ACE Engine用）に変換しておくことで、この「接続の相性問題」を確実に回避できます。

まとめ
手順はソースファイルと同じ（[名前を付けて保存] ＞ [accdb]）。

DB側も変換したら、ソース側で「リンクの張り直し」を忘れずに。

「ソースもDBもaccdb」という状態にするのが、64bit化における最も安全なゴールです。

これで、データとプログラムの両方が最新の土台に乗ることになります。あとはVBAの型修正に集中できますね！

次に気になっていることや、実際の変換でエラーが出た箇所はありますか？

コンバージョンの作業は、コンパイルが通ればほぼ終わりでしょうか？

コンパイルが通ることは「大きな山を越えた」と言えますが、残念ながら「コンパイル成功＝コンバージョン完了」ではありません。

特に32bitから64bitへの移行、かつAccess 2000という非常に古いバージョンからの移行では、「コンパイルは通るけれど、動かすと落ちる（または正しく動かない）」というパターンがいくつか残っているからです。

コンパイル後に確認すべき「最終チェックリスト」を整理しました。

1. 実行時エラー（ランタイムエラー）の確認
前にお話しした通り、LongPtr にすべき場所を Long のままにしていると、コンパイルは通りますが、実行してそのコードを読み込んだ瞬間に Accessが強制終了（クラッシュ） します。

チェック方法: APIを呼び出している画面やボタンを一通り実際にクリックして、動作を確認してください。

2. 外部ライブラリとActiveXコントロール
Access 2000時代によく使われていた機能で、64bit版では「存在すらしていない」ものがあります。

カレンダーコントロール: 昔のカレンダー機能は64bitでは動きません。

TreeView / ListView: これらも64bit版Officeでは標準で提供されていないため、表示されなかったり、エラーになったりします。

これらはコンパイルエラーではなく、「画面を開こうとした時にエラー」になります。

3. 文字列の扱い（API周り）
Windows APIの中には、32bitと64bitで「構造体（データの詰め合わせ）」のサイズが変わるものがあります。

APIに渡す自作の「Type（構造体）」を使っている場合、その中身の Long も LongPtr に変える必要があるケースがあります。ここがズレていると、APIから変な値が返ってきたりします。

4. リンクテーブルとファイルパス
今回、CurrentProject.Path などを使ってリンクを自動更新するようにされたと思いますが、それが本番環境のサーバーパスでも正しく動くかのテストが必要です。

自分のPCでは動いても、共有フォルダに置くと権限の問題でリンク更新に失敗することがあります。

5. 印刷とレポート
Access 2000から最新版への移行では、レポート（帳票）のレイアウトが微妙に崩れることがあります。

フォントの幅が変わったり、プリンタドライバの解釈が変わることで、「1ページに収まっていたものが2ページになる」といったことが起こり得ます。主要な帳票は一度プレビューを確認することをお勧めします。

💡 理想的な「終わらせ方」
以下の手順まで終えれば、自信を持って「完了」と言えます。

[デバッグ] ＞ [VBAProjectのコンパイル] がグレーアウトしている（＝エラーなし）。

すべてのフォームを開き、すべてのボタンを一度は押してみる。

リンクテーブルの更新がエラーなく完了し、データが正しく表示される。

.accde ファイル（実行専用ファイル）を作成してみる。

[ファイル] ＞ [名前を付けて保存] ＞ [ACCDE の作成] が正常にできれば、VBAの構造に致命的な矛盾がない証拠になります。

もし特定のボタンを押した時に Access が「動作を停止しました」と落ちるようなら、そこが LongPtr の修正漏れ（犯人）です。


■フォームの開き方
Access 2000から最新の .accdb 形式に移行した場合、フォームの開き方にはいくつか方法がありますが、基本は「ナビゲーションウィンドウ」を使います。

以前のバージョンでは「データベースウィンドウ」という独立した画面がありましたが、現在は画面左側の細長いバーに集約されています。

1. ナビゲーションウィンドウから開く（基本）
画面左側にある [ナビゲーションウィンドウ] を確認します。

もし表示されていない場合は、F11 キーを押すと表示/非表示を切り替えられます。

「フォーム」のグループを探します。

開きたいフォーム名を ダブルクリック します。

編集（デザイン）したい場合: フォーム名を右クリックして [デザインビュー] を選択します。

2. VBAコードから開く（自動化）
ボタンをクリックしたときなどに、他のフォームを自動で開きたい場合は、以下の1行を書きます。

VBA
DoCmd.OpenForm "フォーム名"
もし、特定のデータ（例えば ID が 10 のもの）だけを表示して開きたい場合は、このように書きます。

VBA
DoCmd.OpenForm "フォーム名", , , "ID = 10"
3. ファイルを開いた時に自動で開く（起動設定）
Accessを起動した瞬間にメニュー画面などを表示させたい場合の設定です。

[ファイル] タブ ＞ [オプション] をクリックします。

左側のメニューで [現在のデータベース] を選択します。

[フォームの表示] というプルダウンメニューから、最初に開きたいフォームを選択します。

「OK」を押し、一度ファイルを閉じて開き直すと、設定したフォームが自動で立ち上がります。

💡 コンバージョン後の注意点
もしダブルクリックしてもフォームが開かない、あるいは開いた瞬間にエラーが出る場合は、以下の可能性があります。

ActiveXコントロールのエラー:
前にお伝えした通り、古いカレンダーやツリービューを使っていると、フォームが開く瞬間に「オブジェクトがありません」等のエラーで止まることがあります。

「Form_Open」や「Form_Load」のVBAエラー:
フォームが開く際に実行されるVBAコードの中に、まだ修正が必要なAPI（PtrSafe 未対応など）が含まれている可能性があります。

まずは F11 キーで左側のウィンドウを出して、一つずつダブルクリックで開けるか試してみてください。無事に開けば、そのフォームの画面周りのコンバージョンは成功です！
